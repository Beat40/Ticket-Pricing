Operational Architecture

Technical specification for the production deployment of the English Premier League (EPL) Ticket Pricing Intelligence system.

SECTION 0 — HOW TO READ THIS DOCUMENT

0.1 Data Generation vs. Operational Scripts

This document focuses exclusively on Operational Scripts. While match_data_generator_epl.py was used to create the synthetic historical record for training, it is not part of the live pricing loop. Operational scripts are those that ingest live signals (standings, weather, velocity) to produce pricing decisions during the season.

0.2 The Concept of Cadence

Components run at different frequencies based on data volatility:

  • Annual: conjoint_engine_epl.py and full model retraining. Fan preferences and historical baselines are relatively static.
  • Monthly: NeuralProphet updates to capture mid-season booking curve shifts.
  • Weekly (Per-Matchweek): Demand model refreshes and StakesEngine recalibrations after weekend results.
  • Daily: EPLLPOptimizer runs for all "Active Matches."
  • Hourly (T-48 to T-0): Rapid re-optimization as the match approaches to capture late-breaking star power or weather changes.

0.3 Active Matches

An "Active Match" is any fixture currently in its sales window (typically T-56 days to Kickoff). At any point in the season, 5-10 matches are active and subject to daily pricing adjustment.

0.4 Live Signals

The system distinguishes between Static Features (known at scheduling) and Live Signals (volatiles). Live signals used in the POC include:

  • velocity_T14 / velocity_T7 (Cumulative sales vs. historical medoids)
  • match_stakes_score (Calculated from live table standings)
  • weather_severity_score (0-4 UK-specific scale)
  • star_power_index (Aggregated player ratings from announced lineups)
  • european_midweek_fatigue (Status of clubs in continental competitions)

SECTION 2 — stakes_engine.py

2.1 Purpose

Stateless context engine that calculates the commercial urgency of a match. It is called by the Forecasting Engine and the LP Optimizer to quantify "Importance."

2.2 Class Definition

class StakesEngine:
    THRESHOLDS = {
        "title": 1, "champions_league": 4, "europa": 6, 
        "conference": 7, "relegation": 17
    }

2.3 Primary Method: compute_stakes_score()

Parameter Type Range Source
home_position int 1-20 Live Standings
matchweek int 1-38 Match Schedule
standings list 20 dicts Live API Data

Urgency Multiplier Formula:

urgency = 0.1 + (matchweek - 1) * (0.9 / 37)
Matchweek110203038
Urgency0.100.320.560.801.00

Combination Logic:

The engine calculates scores for Title, Top 4, Relegation, and European spots, then selects the dominant narrative using max():

raw_score = max(title_score, top4_score, relg_score, euro_score)

2.4 Output Schema

  • match_stakes_score: float [0.0 - 1.0]
  • match_stakes_label: string ("Title Decider", "Standard", etc.)
  • urgency: float [0.1 - 1.0]

SECTION 3 — conjoint_engine_epl.py

3.1 Purpose

Run annually to derive Willingness-To-Pay (WTP) bounds. It uses Hierarchical Bayesian Multinomial Logit (HB-MNL) to model fan heterogeneity.

3.2 Configuration

  • Model: PyMC mu_price ~ Normal(-3.0, 1.0) (Prior assumes cost is a disutility).
  • Sampling: draws=1000, tune=500, chains=2.
  • Expected Runtime: ~15 minutes per tier on modern hardware.

3.3 Tier Routing

Matches are routed to WTP profiles based on the home club's tier:

  • big_six → epl_wtp_big_six.json
  • established_mid → epl_wtp_mid.json
  • smaller_club → epl_wtp_small.json

SECTION 4 — inventory_manager.py

4.1 Purpose

Calculates the slice of inventory available for dynamic pricing. The LP Optimizer operates only on this subset.

4.2 Formulas

Dynamic Lower   = capacity × dynamic_inventory_pct × 0.55
Dynamic Upper   = capacity × dynamic_inventory_pct × 0.35
Dynamic General = capacity × dynamic_inventory_pct × 0.10

4.3 Away End Handling

The Away End is strictly fixed at £30 as per League Rules. capacity = min(3000, total_cap * 0.10).

SECTION 5 — forecasting_engine_epl.py

5.1 STL Decomposition (Layer 1)

The engine extracts club-specific trends using Loess (period=19 home games per season). Trends are saved to latest_stl.json for live inference.

5.2 Feature Importance (SHAP)

From forecasting_evaluation.json:

FeatureImportance
stl_seasonal27.09
stl_trend12.19
star_power_index0.70
match_stakes_score0.10

5.3 Predict Mode Sequence

  1. Load pre-trained LightGBM ensemble from epl_lgb.joblib.
  2. Fetch stl_trend and stl_seasonal for the club.
  3. Apply quantile regression for P10 and P90 uncertainty bands.
  4. Return predicted_fill_rate to the Optimizer.

SECTION 6 — lp_optimizer_epl.py

6.1 Purpose

Final decision layer. Finds the revenue-maximizing price point per zone.

6.2 The Linear Demand Curve

q = base_q * (1 + epsilon * (p - median_p) / median_p)

6.3 Elasticity Matrix (ε)

  • Hospitality: -0.10 (Inelastic)
  • Lower Tier: -0.55
  • Upper Tier: -0.75
  • General Sale: -1.10 (Highly Elastic)

6.4 Constraints (PuLP)

# Attendance Floor (Non-Big Six only)
prob += total_attendance >= 0.65 * dynamic_inventory

# Monotonicity
prob += p_hosp >= p_lower >= p_upper >= p_gen

SECTION 8 — OPERATIONAL FLOW

  1. T-45 Days: Match goes on sale. LP runs with baseline demand.
  2. T-14 Days: Live velocity_T14 signal updates demand.
  3. T-1 Day: Star Power updated from announced lineups; LP re-runs for final price adjustments.
  4. T-0: Final price lock.

SECTION 11 — KNOWN LIMITATIONS

MAPE Interpretation: The 21% MAPE in the POC is inflated by synthetic noise used to test "Stress Scenarios." Production values typically hover at 5-8% for Big Six clubs due to near-constant sellout data.
Live Ticketing Webhooks: In this implementation, velocity is computed from daily snapshots. True production requires a real-time webhook from platforms like Ticketmaster to handle high-frequency surges (e.g., general sale opening).
